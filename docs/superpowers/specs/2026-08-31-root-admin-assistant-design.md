# 企业对话业务助手与企业全景设计

## 1. 目标与成功标准

系统提供两个管理员一级入口：

- **管理助手**：root/admin 的知识问答、实时经营查询、页面导航和受控管理操作入口。
- **企业全景**：组织、费用、项目、合同、知识、工单、审批、考勤和薪酬的持续观察入口。

员工继续使用 `/chat`，但 ChatPage 从“知识问答加少量前端关键词判断”升级为完整的对话业务入口。用户可以用自然语言发起请假、工单和报销，查询工单、考勤、排班、请假和费用，也可以打开相应业务页面。

成功标准如下：

1. root/admin 和员工都能正常进行知识问答并看到最终回答，而不是内部流水线状态。
2. 高频业务命令不依赖知识库文档，也不依赖大模型可用性。
3. 查询、表单预填、页面导航和写操作使用统一的服务端协议。
4. 低风险查询直接执行；敏感查询和产生副作用的操作按风险确认。
5. 已有组织、项目、合同、费用、审批、排班、薪酬、工单和知识服务仍是业务规则与事务边界。
6. 企业全景在月初、北京时间和 UTC 日期不一致时仍能正常加载，所有指标可下钻。
7. 管理端的主要导航只保留“管理助手”和“企业全景”；现有详情页面保留为深链。

## 2. 现状与约束

员工 ChatPage 已经具备以下可复用能力：

- `LeaveRequestDialog` 与 `/me/leave-preview`。
- `TicketPreviewDialog` 与 `/tickets/preview`。
- `ExpensePreviewDialog` 与 `/expenses/preview`。
- 知识问答流式输出、引用、会话上下文、文档范围和用户记忆。
- 当日考勤检查、打卡和考勤历史。

当前缺口是这些能力由 ChatPage 顺序执行前端正则和多个 preview 请求，只覆盖创建类意图；“查看工单”“查看本月流水”“查看今天考勤”等查询和导航未进入统一流程。

管理助手已有受控动作注册表、预览、确认、幂等、对象版本检查和审计，但自然语言识别仅支持少量固定别名。低风险查询仍生成动作预览，页面也只渲染 `thread: ready`、`retrieval: running` 等内部事件，没有呈现最终回答或业务结果。

企业全景已有大部分指标和下钻页面。其初始日期分别使用本地时间和 UTC，可能在北京时间月初形成 `start > end`，导致接口返回 422。页面标题仍使用“管理驾驶舱”。

本设计不开放任意 SQL、任意 HTTP 请求、任意前端 URL 或模型自主编写业务调用。真实业务写入只能调用已注册、服务端拥有的业务服务。

## 3. 方案比较与选择

### 方案 A：统一服务端对话业务协议，渐进复用现有 UI（采用）

所有聊天输入先经过统一编排层，输出知识回答、实时查询、表单预览、白名单导航或受控动作。ChatPage 保留现有弹窗和会话能力，管理助手复用统一消息呈现组件。

优点：权限和风险规则一致；已知业务在大模型不可用时仍可工作；现有业务服务和 UI 可复用；后续新增能力只注册一次。代价是需要扩展服务端事件协议，并对两个聊天页面做适度抽取。

### 方案 B：两个页面分别增加关键词和接口调用（不采用）

继续在 ChatPage 和管理助手中各自增加正则、preview 调用和页面跳转。短期改动少，但意图、权限、错误处理和结果展示会持续分叉，无法可靠覆盖“所有操作都能通过问答触发”。

### 方案 C：让大模型直接选择接口或数据库（不采用）

模型自由决定 URL、参数或 SQL。表达能力强，但无法保证权限、审计、事务、幂等和风险确认，不符合企业管理场景。

## 4. 总体架构

```text
用户输入
  -> 身份、角色与数据范围
  -> 规则优先的意图识别
  -> 可选的 LLM 结构化字段补全
  -> 服务端能力注册表校验
  -> 知识问答 / 实时查询 / 表单预览 / 白名单导航 / 动作预览
  -> 风险策略
  -> 直接返回或等待确认
  -> 调用现有业务 service
  -> 保存消息与审计记录
  -> 聊天文本、结果卡片、弹窗或页面跳转
```

编排层只负责理解用户意图、校验能力和选择业务入口。它不复制组织、费用、审批、项目、合同、知识、排班、薪酬和工单的业务逻辑。

### 4.1 统一响应类型

对话响应分为五类：

1. `answer`：知识库检索、流式回答、引用和溯源检查。
2. `query_result`：实时只读业务数据，包括汇总、列表和可下钻目标。
3. `form_preview`：无副作用的表单预填，包括缺失字段和可编辑字段。
4. `navigation`：服务端白名单中的业务页面，不接受模型生成的任意 URL。
5. `action_preview`：会产生副作用的管理动作，沿用现有动作生命周期。

`/chat/ask` 保持 SSE 传输，并扩展为稳定的业务事件。前端不再把底层节点直接展示给用户。旧的 `thread`、`answer` 和 `final` 事件保持兼容，新增事件包含明确的 `kind`、`intent`、`display`、`payload` 和可选的 `route_key`。

### 4.2 意图识别

采用“规则优先、LLM 补全、注册表复核”：

- 高频明确命令由服务端规则识别，保证稳定和离线可用。
- 复杂表达可以调用 LLM 提取候选 intent 与字段，但只返回结构化候选。
- 服务端用 Pydantic 模型、角色、数据范围和注册表重新验证。
- 未注册能力、任意 URL、SQL、提示词中的风险降级要求均被拒绝。
- 无法确定业务意图时才进入知识问答或返回澄清信息，不能误执行写操作。

规则至少覆盖：项目、部门、合同、文档、工单、审批、费用、当日考勤、本月费用；请假、工单、报销预填；打开工单、费用、组织、项目、合同、知识、排班、薪酬和企业全景。

## 5. 员工 ChatPage

ChatPage 保留现有会话、文档范围、记忆、引用和三个业务弹窗。前端分散的 `shouldPreview*` 判断迁移到统一编排结果；在迁移期间仅作为兼容兜底，不能成为最终权限边界。

### 5.1 创建与预填

- “我要请假三天，家里有事”返回 `form_preview: leave`，自动填入类型、开始日期、结束日期和原因，缺失字段由用户补充，确认后提交。
- “电脑网络有问题，帮我找信息部处理”返回 `form_preview: ticket`，预填工单类型、部门、处理人、主题和描述，确认后提交。
- “报销昨天打车 86 元”返回 `form_preview: expense`，预填标题、用途、金额、类别和明细，确认后创建费用草稿。
- 生成表单预览不产生副作用；提交必须由用户确认。

### 5.2 查询与导航

- “查看工单”直接打开 `/collaboration`，因为导航可逆且无副作用。
- “看看我有哪些未完成工单”在聊天中返回可见工单摘要卡，并提供进入工单中心的按钮。
- “查看这个月流水”“本月支出怎么样”返回本人可见费用的笔数、总额和状态分布，并提供带月份筛选的费用页面入口。
- “查看我的考勤”“查看排班”“查看请假记录”返回实时数据卡片或打开现有历史界面。
- “打开费用报销”“进入组织信息”等明确导航指令直接跳转到白名单路由。

查询结果严格复用已有可见性规则。员工不能通过聊天看到同事费用、其他部门工单或管理员汇总。

## 6. root/admin 管理助手

管理助手改为完整聊天界面：用户消息、助手文本、引用、结构化结果卡、表单预览、风险确认和执行结果。`node/status` 只用于内部诊断，不作为普通消息展示。

### 6.1 实时管理查询

支持项目、部门、合同、文档、工单、审批、费用和考勤等实时数据查询。示例：

- “查询一下最近的项目”直接执行项目查询并显示列表。
- “查看一下今天考勤”返回应出勤、已登记、未登记、正常、迟到、缺勤和远程人数。
- “查看本月支出”返回当前权限范围内的费用汇总和状态分布。
- “列出待审批费用”“查看未完成工单”返回结构化结果和下钻入口。

root 无部门归属时默认覆盖所有部门；其他角色继续使用已有角色与部门范围。密码、令牌、加密字段和未授权个人信息永不返回。

### 6.2 管理操作

现有动作注册表继续覆盖组织、项目、合同、文档、费用、请假、工单、审批、付款、删除和薪酬生成。自然语言规划只产生注册表中的动作计划，写操作仍由现有 service 执行。

低风险查询不再创建需要点击确认的动作预览，而是直接执行并返回 `query_result`。敏感查询、普通写操作、高风险操作和批量操作按风险策略进入确认流程。

## 7. 风险、确认与审计

| 等级 | 示例 | 行为 |
| --- | --- | --- |
| 低风险 | 汇总查询、普通列表、白名单导航、表单预填 | 直接执行或打开 |
| 敏感查询 | 薪资、个人费用明细、联系方式、考勤明细、敏感事件 | 权限校验后确认查看 |
| 普通写操作 | 提交请假、工单、报销，创建或修改业务对象 | 显示预览后确认 |
| 高风险 | 审批、付款、删除、改薪、离职、权限变更 | 显示影响与前后差异后明确确认 |
| 批量操作 | 批量发薪、批量删除、跨部门批量变更 | 两次确认 |

确认动作绑定用户、线程、工具、参数摘要、对象版本、过期时间和幂等键。确认时服务端重新校验角色、数据范围、参数摘要、对象版本和动作状态。参数变化、对象被修改、动作过期或跨线程确认均拒绝执行，并要求重新生成预览。

预览、确认、取消、过期、权限拒绝、执行成功和执行失败均写入审计。模型输出的“已完成”不能作为业务成功依据；成功必须来自服务端事务结果。

## 8. 企业全景与两入口信息架构

`/admin/overview` 使用“企业全景”名称，`/admin/dashboard` 保留重定向兼容。管理员默认进入 `/admin/assistant`。

管理端主导航只保留：

- 管理助手
- 企业全景

组织、排班、项目、合同、知识、工单、费用、薪酬和敏感记录页面不删除，继续作为指标下钻、聊天导航和复杂编辑页面。

企业全景保留并完善：

- 在职员工、部门、待审批、待付款。
- 项目、合同、知识文档、工单、待办和薪酬状态。
- 今日请假、未登记考勤和协作待办。
- 费用状态分布和月度趋势。
- 部门和日期筛选。
- 每张卡片的实际业务页面下钻。
- “向管理助手提问”入口，可携带当前日期和部门筛选。

日期统一使用本地年月日格式函数生成，初始范围保证 `start <= end`。后端继续验证非法范围并返回明确错误。

## 9. 数据流与持久化

所有对话意图都先创建或复用当前线程。用户输入和最终可见回答写入消息历史；内部调试事件不写成可见回答。

- `answer` 保存最终知识回答和引用。
- `query_result` 保存可读摘要；完整列表可以由结果事件临时呈现，避免把大量业务数据塞入聊天历史。
- `form_preview` 保存用户请求；只有确认提交后保存业务结果消息。
- `navigation` 保存简短的助手响应，不保存任意 URL，只保存 route key。
- `action_preview` 使用现有 `AssistantAction` 生命周期与审计记录。

敏感或被阻止的内容按现有上下文标记排除后续模型记忆，避免敏感数据通过聊天历史再次泄露。

## 10. 错误与降级处理

- LLM 未配置或请求失败：已注册规则意图、实时查询、导航和表单预览继续工作；知识问答返回清晰错误。
- 业务查询失败：返回可重试提示，不伪造空结果。
- 参数缺失：返回可编辑表单及缺失字段，不执行写入。
- 权限不足：说明无法执行，但不泄露不可见对象是否存在。
- 对象不存在或并发冲突：动作失效并要求重新查询或预览。
- 页面 route key 不存在：拒绝导航并记录协议错误。
- SSE 中断：已完成的服务端事务不重复执行；前端可刷新线程恢复最终消息。
- 企业全景某个辅助统计接口失败：核心概览仍显示，失败模块展示独立重试状态。

## 11. 测试策略

### 11.1 后端单元与集成测试

- 中文意图矩阵：最近项目、今日考勤、本月费用、查看工单、请假、工单、报销和页面导航。
- 规则优先与 LLM 降级：LLM 不可用时高频意图仍正确。
- 注册表安全：任意 SQL、URL、未注册动作和聊天中的风险降级字段不能执行。
- root 全部门范围、员工个人范围、经理部门范围和财务费用范围。
- 查询 adapter 只返回有界 JSON，不序列化秘密字段。
- 低风险查询直接执行，敏感查询和写操作进入正确确认流程。
- 动作参数摘要、版本、过期、跨用户、跨线程和幂等测试。
- `/chat/ask` SSE 对五类响应产生稳定事件并保存正确消息。
- 企业全景日期范围、月初、权限和费用聚合测试。

### 11.2 前端测试

- 事件到消息、结果卡、表单、导航和确认卡的纯函数映射。
- 管理助手显示最终回答与业务结果，不显示内部 pipeline 节点。
- ChatPage 能打开并预填请假、工单和报销弹窗。
- “查看工单”导航到协作中心，“本月支出”显示汇总并带月份筛选。
- 管理端仅保留两个一级入口，详情深链仍可访问。
- 企业全景初始日期使用本地日期，始终是合法范围。
- 账号切换后会话、结果和业务数据不串号。

### 11.3 浏览器端到端验收

使用真实连接配置验证只读数据，使用隔离测试数据验证写操作：

1. `admin/admin123` 登录并完成知识问答、最近项目、今日考勤、本月支出和页面导航。
2. 管理员创建一个受控动作，验证确认、取消和过期状态。
3. 员工账号完成知识问答、请假预填、工单预填、报销预填、查看工单和本月支出。
4. 验证员工无法看到其他用户或部门的未授权数据。
5. 验证企业全景所有关键指标和下钻链接。
6. 关闭或模拟 LLM 失败，重新验证高频业务命令。

真实数据库不做破坏性测试。写操作测试优先使用事务测试库；若必须在真实数据库验证，只创建明确标记的测试记录，并通过正常业务接口清理或保留可审计记录。

## 12. 非目标

- 不开放任意 SQL、任意 HTTP、任意 URL 或模型自主工具注册。
- 不删除现有业务详情页面。
- 不提升员工权限或绕过现有数据范围。
- 不在本次改造中重写整个 ChatPage；只抽取服务本次统一协议所需的共享组件。
- 不以模型文本代替服务端事务、审计和最终状态。
