# Root 管理员双入口与管理助手设计

## 1. 目标与范围

root 管理员目前只能进入管理后台页面，不能使用已有知识问答链路；业务操作也分散在多个页面。本次改造将 root 管理员的工作入口收敛为两个一级入口：

- **管理助手**：知识问答、经营查询和业务操作的统一对话入口。
- **企业全景**：关键指标、风险提醒、待办和结果核验的统一总览入口。

现有详情页面继续保留为深链或抽屉内容，不再作为主导航中的一级功能。员工端现有问答和业务流程继续保留并兼容。

本设计覆盖：root 的知识检索、受控业务工具、风险确认、审计、前端双入口和回归测试。它不引入新的任意 SQL 能力，也不改变现有业务服务对数据一致性的负责边界。

## 2. 核心架构

```text
用户输入
  -> 身份与数据范围
  -> 意图规划
  -> 知识检索 / 数据查询 / 业务工具
  -> 参数校验
  -> 风险判断
  -> 直接返回或生成确认动作
  -> 执行现有业务 service
  -> 审计记录
  -> 返回结果与后续建议
```

新增统一动作层，由服务端维护：

- `action_registry`：工具名称、输入模型、权限要求、风险等级、预览和执行处理器。
- `action_planner`：将自然语言转换为结构化、可验证的动作计划。
- `action_executor`：调用已有组织、费用、审批、项目、合同、知识、排班、薪酬和工单服务。
- `confirmation_service`：创建、校验、过期和消费确认动作。
- `operation_audit`：记录预览、确认、拒绝、过期、执行和失败结果。

AI 只能选择注册工具，不能直接执行 SQL、拼接任意接口或绕过现有 RBAC。现有业务 service 仍是写入、状态流转、版本检查和幂等控制的最终边界。

### root 数据范围

root 管理员没有部门归属时，知识检索和管理查询的默认范围为全部部门；也可以在问题中指定一个或多个部门、项目或文档范围。普通员工和非 root 管理员继续使用现有部门、文档所有权和角色范围。范围解析必须在后端完成，不能依赖前端传入的角色判断。

密码、令牌等秘密信息永不通过助手返回。薪资、联系方式、考勤明细和敏感事件属于隐私敏感数据，必须通过角色和范围校验，并留下访问审计。

## 3. 风险与确认

所有写操作统一先生成预览；高风险操作在预览基础上加强确认。

| 等级 | 示例 | 处理方式 |
| --- | --- | --- |
| 低风险查询 | 制度、项目、工单、费用状态、知识文档 | 有权限即可直接返回 |
| 隐私敏感查询 | 薪资、联系方式、考勤明细、敏感事件 | 角色和范围校验后仍需明确确认；跨部门或批量查看再增加二次确认 |
| 普通写操作 | 新建部门、项目、合同、文档、工单、请假、费用草稿、待办 | 预览后确认执行 |
| 高风险写操作 | 审批、付款、改薪、重置密码、离职、删除、权限变更、批量变更 | 影响范围、前后差异、不可逆提示；明确确认 |
| 批量或跨部门操作 | 批量删除、批量调岗、跨部门导出、全员通知 | 二次确认，并要求输入明确确认词 |

确认动作的服务端结构如下：

```json
{
  "action_id": "act_xxx",
  "tool": "update_employee",
  "risk": "high",
  "summary": "将员工张三调入研发部，职位改为高级工程师",
  "changes": [
    {"field": "部门", "before": "交付部", "after": "研发部"},
    {"field": "职位", "before": "工程师", "after": "高级工程师"}
  ],
  "affected_records": 1,
  "expires_at": "2026-08-31T15:10:00Z",
  "requires_confirmation": true
}
```

执行时服务端重新校验：当前用户与角色、目标对象、动作参数摘要、对象版本、确认令牌有效期和幂等键。原始指令改变、对象被其他人修改或动作过期时，拒绝执行并要求重新预览。确认、取消、过期和执行结果全部写入审计日志。

助手后续消息中的“确认执行”只允许消费当前会话最近生成且仍有效的动作；不能用模糊确认消费其他会话、其他对象或已修改参数的动作。

## 4. 管理助手

root 登录后默认进入 `/admin/assistant`。页面以一个主要对话区为中心，历史会话和上下文设置默认收起；右侧仅在需要时展示查询结果、操作预览、确认面板或执行进度。

支持的返回类型：

- 知识回答：正文和引用来源。
- 数据查询：表格、统计卡片和当前筛选范围。
- 操作预览：变更前后、影响对象和风险等级。
- 确认面板：确认、取消、修改参数。
- 执行结果：成功、部分成功、失败和可重试动作。

以下问题都应由同一入口处理：

```text
查一下研发部今年的费用趋势
把张三调到研发部
审批编号 EXP-20260831-001
删除已经过期的知识文档
把本月所有待付款费用列出来
```

管理助手复用员工端知识问答的流式事件和引用展示，但业务动作使用新的结构化动作事件，不再依赖前端关键词分流。员工端可以继续保留现有预览组件，并逐步迁移到同一动作协议。

## 5. 企业全景

`/admin/overview` 替代原“管理驾驶舱”作为第二个一级入口，面向持续观察和快速下钻：

- 员工、部门、项目、合同、知识文档、费用、薪酬和工单关键指标。
- 待审批、待付款、逾期工单和知识库异常等风险提醒。
- 最近高风险操作和审计事件。
- 费用趋势、人员变化和项目预算趋势。
- 全部部门、单部门、项目和文档范围筛选。
- “交给管理助手处理”按钮，把当前卡片筛选条件带入助手。

原有页面不删除，改为详情深链或从卡片、查询结果中打开的抽屉。这样保留复杂表格和编辑能力，同时减少主导航和常驻窗口。

## 6. 路由与兼容

- root 管理员默认跳转 `/admin/assistant`。
- `/admin/overview` 是企业全景入口。
- 原 `/admin/dashboard` 重定向到 `/admin/overview`，保留旧链接兼容。
- 其他 `/admin/*` 页面继续可访问，但从主导航移除。
- 员工仍默认进入 `/chat`，不获得 root 的全量部门范围。
- 服务端 `/chat/ask` 扩展为支持 root 的全部知识范围和结构化动作事件；线程、引用、敏感门禁和现有流式协议保持兼容。

## 7. 错误处理与一致性

- 规划失败：返回可理解的澄清问题，不调用写工具。
- 参数缺失或不合法：返回缺失字段和可修改的预览，不落库。
- 权限不足：说明所需角色或数据范围，不泄露不可见对象的细节。
- 目标不存在：明确指出对象未找到，并提供可选查询条件。
- 并发版本冲突：动作失效，重新读取对象并生成新预览。
- 部分批量失败：返回每个对象的成功、失败和失败原因；成功项不重复执行。
- 服务异常：保留失败审计记录，返回幂等重试建议。

## 8. 测试与验收

### 后端

- root 在无部门归属时可检索全部部门知识，员工不能越权。
- 每个注册工具都执行权限、参数和对象范围校验。
- 普通写操作没有有效确认动作不能落库。
- 高风险操作没有二次确认不能执行。
- 参数摘要、对象版本或令牌过期后执行被拒绝。
- 幂等键阻止重复付款、审批和创建。
- 审计记录覆盖预览、确认、取消、过期、成功、失败和拒绝。
- 现有员工端聊天、请假、报销、工单和敏感门禁回归通过。

### 前端

- root 默认进入管理助手，顶部只保留管理助手和企业全景两个一级入口。
- 知识回答、查询结果、预览卡片、确认卡片、进度和错误状态正确渲染。
- 确认卡片只能消费当前有效动作，取消和过期状态清晰可见。
- 企业全景卡片能携带筛选条件跳转管理助手。
- `/admin/dashboard` 旧链接正确重定向。
- 原有详情页深链仍可打开，账号切换后数据隔离不回归。

### 验收标准

root 不打开原有后台页面，仅通过管理助手和企业全景即可完成知识查询、经营查询和所有已注册管理操作；任何高风险动作都无法绕过确认和审计。

## 9. 非目标

- 不在本次改造中开放任意 SQL、任意 HTTP 请求或模型自主编写业务代码。
- 不删除现有业务页面和后端 service。
- 不把员工端权限提升为 root 的全局范围。
- 不把“模型说已完成”视为业务成功；成功必须以服务端事务和审计结果为准。
